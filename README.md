# Envoy Ring Buffer Cache & Request Coalescing

## How I solved it and why
I implemented the cache and request coalescing as a standalone HTTP filter (`source/extensions/filters/http/ring_buffer_cache/`) instead of using Envoy's existing `cache` extension. I looked at the built-in cache folder first, but its interfaces are very strict and abstract away the stream lifecycle. Because the main requirement here was to pause duplicate requests and stream body chunks to them immediately so Envoy's idle timers don't drop the connection, writing a standalone `Http::StreamFilter` (`decodeHeaders`, `encodeHeaders`, `encodeData`) gave me direct control over `StopIteration` and injecting chunks.

For the data structures:
- **Global Cache (`GlobalRingBufferCache`):** An `unordered_map` keyed by `host + url` that returns a `std::shared_ptr<CachedResponse>`.
- **Ring Buffer (`CachedResponse`):** Each URL entry holds response headers and a `std::deque<Buffer::OwnedImpl>` for body chunks. I chose `std::deque` over `std::vector` because popping old chunks from the front of a vector is O(N) and shifts memory, while `std::deque` does front-pop and back-push in O(1) time with better cache locality than `std::list`. Eviction is done per-chunk in `addDataLocked()` whenever `current_size > max_buffer_size` (configured via `envoy.yaml`).
- **Two-tier locking:** There is one global `absl::Mutex` just for looking up/inserting the `shared_ptr` in the map, and a separate `entry_mutex` inside each `CachedResponse`. That way downloading a big file on one URL doesn't block other URLs.
- **Request Coalescing:** Each entry has 3 states: `Empty`, `Fetching`, and `Cached`. On a miss (`Empty`), the first request sets state to `Fetching` and goes to the backend. Any other request arriving while `Fetching` grabs any headers/chunks already received, adds itself to `entry->listeners`, and returns `StopIteration`. As `encodeData` gets chunks from the backend, it pushes them to the ring buffer and immediately posts them to all waiting listeners.

## Where I got stuck and how I got past it
1. **Building Envoy on a Mac with 8GB RAM:** This was honestly the most painful part at the start. Running Bazel inside the Docker dev container kept crashing with OOM (`error code 14, Socket closed`) because Clang + V8 takes ~1.5GB per job. I got past it by switching from `-c dbg` to `-c fastbuild`, increasing Docker swap, and limiting Bazel with `--local_resources=memory=3072 --jobs=3`. The first build took around 1.5-2 hours, but after that incremental builds of my filter only took ~4 seconds.
2. **Envoy boilerplate & cross-thread crashes:** Since I didn't know Envoy's internal C++ APIs by heart, I used docs and AI to help wire up the `Http::StreamFilter` virtual methods and the `NamedHttpFilterConfigFactory` registration macro. I also initially thought I could just loop over `entry->listeners` in `encodeData` and call `encodeData` on each waiting filter directly. That crashes in Envoy because requests sit on different worker threads. To fix it, I saved each follower's `Event::Dispatcher*` and used `dispatcher->post(...)` with a shared `std::atomic<bool> alive_flag_` (flipped to `false` in `onDestroy()`) so chunks are delivered on the follower's own thread and don't touch destroyed streams if a client disconnects early.
3. **Abseil thread-safety compiler errors:** Envoy compiles with `-Wthread-safety`. When I tried writing directly to `entry->response_headers` inside the `headers.iterate(...)` lambda, Clang complained that `entry_mutex` wasn't held inside the lambda scope. I fixed it by writing into a local `temp_headers` vector first and moving it into `entry->response_headers` outside the lambda.

## How else it could be solved & how it scales
- **Thread-Local Storage (TLS) vs Global Map:** The "Envoy way" is usually a thread-local cache per worker thread with zero locks. That scales much better for CPU, but if you have 16 worker threads, 16 requests would still hit the backend during a thundering herd and use 16x RAM. A global map solves the thundering herd globally (only 1 request hits backend), though in a huge production setup I would shard the global map (e.g. 64 buckets with separate mutexes) so the map lock never becomes a bottleneck.
- **Performance & Memory:** Chunk-level eviction in `std::deque` is O(1), which is fast. However, right now when broadcasting chunks across threads via `dispatcher->post`, it copies the chunk string (`data.toString()`). Also, as required by the task, the total number of URLs in `cache_map_` is unbounded, so in real production it would eventually run out of RAM without a global LRU/TTL eviction policy.
- **Maintainability & Security:** The code is ~250 lines isolated in one extension folder, so it's easy to read. For security/correctness, right now it caches any HTTP 200 GET response and ignores `Cache-Control: private/no-store` or `Authorization` headers, which you would obviously need in production so you don't leak one user's data to another.

## What could be improved (and why I didn't do it now)
- **Primary fetcher failure recovery:** If the primary client disconnects mid-download (`onDestroy`), waiting followers should be woken up via `continueDecoding()` or one promoted to primary. I kept `onDestroy` minimal (`alive_flag_ = false`) so the core coalescing flow stays simple and easy to trace.
- **TTL / HTTP headers:** Respecting `Cache-Control` max-age and adding LRU eviction for old keys.
- **Watermarking (Backpressure):** Not implemented in code as stated in the task. To make watermarking work across HTTP/1.1, HTTP/2, and HTTP/3: watermark buffers (`Buffer::WatermarkBuffer`) stop fast upstreams from OOMing Envoy when a downstream client is slow (pausing reads at high watermark, resuming at low watermark). With 1-to-N coalescing, one slow client shouldn't stall 99 fast ones. We would need per-listener read offsets inside the ring buffer and subscribe to `DownstreamWatermarkCallbacks`. When a follower hits high watermark, we stop pushing to its buffer and let it lag behind in the ring buffer until `onBelowWriteBufferLowWatermark()` fires. If it lags so much that the ring buffer is about to evict chunks it hasn't read yet, we either throttle upstream (`readDisable(true)`) or drop/detach that slow client. Across protocols, backpressure maps to TCP window size (`readDisable`) in HTTP/1.1, per-stream `WINDOW_UPDATE` frames in HTTP/2, and QUIC `MAX_STREAM_DATA` frames over UDP in HTTP/3.
